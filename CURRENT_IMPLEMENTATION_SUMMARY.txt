2. AUTHENTICATION & ROLE-BASED ACCESS CONTROL (RBAC)
================================================================================

ROLES IMPLEMENTED:
- CITIZEN:
  Can submit reports, view own reports, inspect case operational progress.
  Strictly blocked from staff queues, case status updates, and staff assignments.
- STAFF:
  Can access routing review queue, staff case queue, perform state transitions,
  assign staff, and add operational notes (scoped to department/authority).
- ADMIN:
  Global municipal oversight with full write and override permissions across all
  authorities and departments.

SECURITY IMPLEMENTATION:
- Server-Derived Identity:
  The client never passes user_id, role, authority_id, or department_id in write
  payloads. The server extracts the verified identity directly from the JWT session
  token in backend/src/middleware/requireAuth.js.
- Client Role Stripping on Registration:
  In POST /api/auth/register-sync, any client-supplied role parameter is discarded;
  new user records are always inserted with role = 'CITIZEN'.
- IDOR Protection:
  Citizen endpoints verify that report.user_id === req.user.id. Unauthorized access
  attempts return 403 Forbidden.
- Departmental Scoping:
  Staff members cannot update or assign cases belonging to an authority or
  department outside their assigned scope.

   - id                     UUID PRIMARY KEY
   - auth_uid               VARCHAR(128) UNIQUE NOT NULL
   - name                   VARCHAR(255) NOT NULL

   - authority_id           UUID REFERENCES authorities(id)
   - department_id          UUID REFERENCES departments(id)
   - created_at             TIMESTAMP WITH TIME ZONE NOT NULL
   - updated_at             TIMESTAMP WITH TIME ZONE NOT NULL

   - id                     UUID PRIMARY KEY
   - user_id                UUID NOT NULL REFERENCES users(id)

   - latitude               DOUBLE PRECISION NOT NULL (-90 to +90)
   - longitude              DOUBLE PRECISION NOT NULL (-180 to +180)
   - location_accuracy      DOUBLE PRECISION (>= 0)

5. CORE LOGIC SERVICES & ENGINES
================================================================================

1. AI ISSUE UNDERSTANDING ENGINE (aiService.js)
   - Uses Google Gemini 3.6 Flash (@google/genai) for multimodal text and image understanding.
   - Strict Separation: Analyzes WHAT the problem is; strictly prohibited from determining
     administrative ownership or municipal authorities.
   - Validates output category against enum list, checks confidence in [0.0, 1.0].
   - If confidence < 0.70 or description is ambiguous, flags as NEEDS_REVIEW.
   - Built-in heuristic fallback engine runs automatically if Gemini quota is exhausted or API key is absent.

2. GEOSPATIAL & JURISDICTION ENGINE (jurisdiction.js)
   - Runs PostGIS spatial query with ST_Covers and temporal validity:
     WHERE ST_Covers(geometry, ST_SetSRID(ST_MakePoint(lng, lat), 4326))
       AND valid_from <= report_time
       AND (valid_until IS NULL OR valid_until > report_time)
   - Resolves into 3 deterministic cases:
     * MATCHED: Exactly 1 boundary polygon covers point (requires_review = false)
     * NO_JURISDICTION_MATCH: 0 boundaries match (outside city or gap; requires_review = true)
     * JURISDICTION_CONFLICT: >=2 overlapping boundaries match (dispute; requires_review = true)
   - Emulates ST_Covers via ray-casting with boundary tolerance in fallback store.

3. DYNAMIC CIVIC RESPONSIBILITY RULE ENGINE (responsibility.js)
   - Resolves WHO is responsible based on (jurisdiction, category, timestamp).
   - Resolves into 3 deterministic cases:
     * ROUTED: Exactly 1 active rule matches (requires_review = false)
     * NO_RESPONSIBLE_RULE: Category unmapped in jurisdiction (requires_review = true)
     * RESPONSIBILITY_CONFLICT: Equal-priority competing rules match (requires_review = true)
   - AI Uncertainty Interlock: If AI confidence < 0.70, marks routing snapshot as NEEDS_REVIEW.

4. ROUTING CONFIDENCE & ASSESSMENT ENGINE (routingAssessment.js)
   - Principle: Automate when confident; escalate when uncertain; never guess responsibility.
   - Evaluates AI + PostGIS + Responsibility Rule signals:
     * AUTO_ROUTED: Valid report + AI confidence >= 0.70 + single spatial match + single rule match.
     * NEEDS_REVIEW: Flagged with structured reasons (AI_LOW_CONFIDENCE, AI_NEEDS_REVIEW,
       NO_JURISDICTION_MATCH, JURISDICTION_CONFLICT, NO_RESPONSIBILITY_RULE,
       RESPONSIBILITY_CONFLICT, INVALID_LOCATION).
   - High AI confidence (e.g. 0.99) can never bypass spatial disputes or unmapped rules.

5. CASE LIFECYCLE SERVICE (caseService.js)
   - Enforces linear state transitions:
     UNASSIGNED -> ASSIGNED -> ACKNOWLEDGED -> IN_PROGRESS -> RESOLVED -> CLOSED
   - Allows structured pauses: IN_PROGRESS -> ON_HOLD and ON_HOLD -> IN_PROGRESS.
   - State transition validation rules:
     * ASSIGNED -> RESOLVED is rejected (400)
     * RESOLVED -> IN_PROGRESS is rejected (400)
     * ON_HOLD requires structured reason (WAITING_FOR_MATERIAL, WEATHER, ACCESS_BLOCKED,
       REQUIRES_EXTERNAL_TEAM, OTHER)
     * RESOLVED requires resolution note describing the fix
     * RESOLVED != VERIFIED: RESOLVED means staff claims completion; independent verification
       is intentionally deferred to Phase 8.
   - Idempotent case creation: AUTO_ROUTED or approved human review creates exactly one case.

7. WORKING OPERATIONAL FLOWS
================================================================================

FLOW 1: HIGH-CONFIDENCE AUTO-ROUTING & RESOLUTION
  1. Citizen submits report: "Huge dangerous pothole near railway gate in Ward 42" with GPS (12.315, 76.635).
  2. AI analyzes report -> POTHOLE, HIGH severity, confidence 0.88.
  3. Geospatial engine matches coordinates -> MCC_WARD_42 (2026-V1).
  4. Responsibility engine resolves rule -> MCC authority, MCC_ROADS department (ROUTED).
  5. Routing assessment confirms all signals -> AUTO_ROUTED.
  6. Operational case created automatically -> CIV-2026-010001 (UNASSIGNED).
  7. Staff opens case -> assigns to Radha Shastry (MCC Ward Officer) -> status moves to ASSIGNED.
  8. Staff acknowledges receipt -> status moves to ACKNOWLEDGED (acknowledged_at recorded).
  9. Work begins on site -> status moves to IN_PROGRESS (started_at recorded).
  10. Staff adds field note: "Inspection completed. Deep pothole excavation finished."
  11. Work complete -> staff marks RESOLVED with note: "Pothole filled and road surface restored."
  12. Citizen views report -> sees complete 5-stage progress and timeline.

FLOW 2: AMBIGUOUS INCIDENT ESCALATED TO HUMAN REVIEW
  1. Citizen submits report outside municipal boundary or with ambiguous text.
  2. Routing assessment detects uncertainty -> flags report as NEEDS_REVIEW.
  3. Operational case is NOT created while under review.
  4. Staff opens /staff/routing-review, reviews details, and clicks Override Route -> assigns MCC / MCC_DRAINAGE.
  5. Review is saved in routing_reviews with audit trail -> report status becomes REVIEWED.
  6. Operational case is automatically created in UNASSIGNED state for newly assigned department.

FLOW 3: WORK PAUSED (ON-HOLD HANDLING)
  1. Active case is IN_PROGRESS.
  2. Staff clicks Put On Hold -> modal requires selecting a structured reason (e.g. WAITING_FOR_MATERIAL)
     and an explanatory note.
  3. Case moves to ON_HOLD (CASE_ON_HOLD event recorded).
  4. When supplies arrive, staff clicks Resume Work -> case returns to IN_PROGRESS (CASE_RESUMED event recorded).
  5. Both events are permanently preserved in the immutable timeline.
